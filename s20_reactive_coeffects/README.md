## 上一章留下的问题

s14 的 `require()` 只回答了"装载时缺依赖怎么办"（抛异常），
没回答运行时的问题：

- 依赖者激活之后，provider 被卸载了 —— 谁通知依赖者？
- 依赖重新出现 —— 依赖者会自动复活吗？
- 卸载一个 provider 时，它和它的依赖者**谁先停**？
  如果 provider 先撤逆，依赖者就会读到"半撤掉的依赖"。

## 这一章解决什么

两件事，都是 dsh 最独门的内容：

**1. 依赖满足性在运行时持续重判。** 每次 provide/unprovide 都对照
每个组件的**声明**分类：

```
activating    σ ⊭ d 且 σ′ ⊧ d   依赖刚被满足 → 激活
deactivating  σ ⊧ d 且 σ′ ⊭ d   依赖刚被撤走 → 停用
neutral       其余               与此组件无关
```

**2. 级联卸载的三段顺序**（Cordis 论文 §4.3.1）：

```
① 停供   provider 先撤下自己的 key（依赖者立刻重算）
② 守卫   provider 等所有依赖者（含间接）都停完 —— 级联，自底向上
③ 撤逆   最后才执行 provider 自己的逆
```

## 新增的核心概念

### 1. 单源纪律（single-source）

一个 key 最多一个 provider。没有它，"谁在提供 db"就回答不了，
target/committed 的比较（s21）和级联顺序都无从谈起。

### 2. 分类对照的是**声明**，不是"key 变了没变"

一个组件只关心"我的依赖集合整体是否从满足翻到不满足"。
无关组件根本不被打扰 —— 这是 O(依赖者) 而非 O(全部组件) 的传播。

### 3. 停供 ≠ 卸载

`unprovide` 只是撤下 key；组件的效应**还没撤**。依赖者先看到
"不可满足"，开始自己的 teardown —— 论文里 L-Leave
（标记 UNLOADING 先于一切逆）的工程形态。

### 4. 守卫：依赖者的逆先于 provider 的逆

demo 的流水直接展示顺序：app 和 cache 的逆都撤完之后，
db 的逆才执行。依赖者永远读不到"半撤掉的依赖"——论文定理 63 的工程形态。

```sh
python s20_reactive_coeffects/code.py --demo
```

五幕：声明与单源纪律 → 反应式激活 → 单源纪律执行 → 级联卸载 → 依赖回来自动复活。

## 为什么这样设计

**为什么"等依赖出现"而不是"启动时报错"**：s14 的 `require()` 只能表达静态
依赖。真实生态里（Koishi 的 4000+ 插件），插件和它的依赖通常由**不同作者**
编写，唯一共享的就是那个 key。依赖暂时缺席是常态：组件应该安静等待，
而不是让整个系统启动失败。

**为什么停供和撤逆分离**：如果 provider 的逆先跑（比如先关掉数据库连接），
依赖者在停用的 teardown 里就再也访问不到它了。所以：

> 先让世界知道"我不再提供了"，等所有依赖者都安全落地，
> 再动手撤自己的资源。

## 与 s14 相比发生了什么

| | s14 | s20 |
|---|---|---|
| 依赖检查时机 | 装载时一次 | **每次上下文变化** |
| 依赖缺席 | 抛异常 | 安静等待，出现即激活 |
| 依赖被撤 | 无人知晓 | **级联停用** |
| 卸载顺序 | 无概念 | **停供 → 守卫 → 撤逆** |
| 单源纪律 | provide 重名即抛 | 正式命名并解释理由 |

## 真实系统里还有什么

- **realm（隔离）**：`ctx.isolate(key, realm)` 让同一个 key 在不同作用域
  解析到不同 provider。我们的 key 是全局的。
- **intercept（拦截）**：上下文携带元数据，右偏合并，让外层**不修改组件**
  就能约束它怎么用依赖（如只读 db 授权）。
- **异步转换**：真实系统的级联是异步的（守卫是 await）。教学版同步递归，
  顺序不变。

## 自己动手改

1. 造一个三级依赖（a → b → c），卸载 a，验证 c 先停、a 最后停。
2. 把分类器改成"对照 key 变了没变"（而不是对照声明），观察无关组件怎么被误触发。
3. 实现 `intercept` 的最简形式：provider 读取时合并上下文元数据，演示"只读授权"。
