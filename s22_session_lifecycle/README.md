## 新增的核心概念

### 1. session/end-seed：种子边界

一条 log-only 事件，标记"它之前的都是种子（恢复/fork 来的），本次生命周期
一条都没产生过"。**为什么需要它**：恢复的会话和原生会话在日志上逐字节相同。
demo 的案例：一条未闭合的 `compaction/start`（压缩锁）——

- 在种子区 → **陈旧证据**，上个生命周期崩溃留下的，忽略
- 在本次区 → **进行中的锁**，必须阻塞新压缩入口

没有 end-seed，恢复后的孤儿锁会被误判成进行中的锁，阻塞一切新压缩 —— 死锁。

### 2. fork：复制 + 打标

因为真相是**不可变的事件流**，分叉才是几行代码的免费操作。如果真相是
可变的 messages 列表，你得深拷贝，还要担心里面的引用共享。

### 3. activation：持久状态与进程权限的分层

s17 把两件事混在了 status 里。dsh 分成两层：

```
durable phase    active / paused / blocked / complete
                 —— 持久状态，写进日志，恢复后还在
activation       armed / disarmed
                 —— 进程级权限，重启即失效
```

"目标还没完成"是持久事实；"允许在没人看着时自动续跑"是**安全决定**。
恢复会话后 automation 不该自己跑起来 —— 等一个人重新 armed。

### 4. 派生缓存：带失效，不是第二份真相

区别：第二份真相允许有人直接往里写；派生缓存**只能被重新计算填满**。
前者迟早坏，后者坏不了。

## 为什么这样设计

**为什么种子边界是事件而不是内存标记**：内存标记（"我加载了 N 条"）在再次
恢复时就丢了。end-seed 是**日志里的事实**，永久、可重放、参与 fork 的复制。

**为什么 fork 需要打标**：子会话的种子历史里有配对检查需要的全部结构
（可能有孤儿锁、有 goal 状态）。不打标，子会话无法区分"继承来的"和
"自己产生的"。

**为什么 activation 故意不进日志**：它是进程级权限。持久化它意味着恢复后
自动续跑自动恢复 —— 那正是要防的风险。"恢复后必须重新授权"这个安全性质，
靠**不持久化**来保证。

## 真实系统里还有什么

- **firstLiveSeq**：dsh 里 `session/end-seed` 的位置就是
  `Session.firstLiveSeq` 的来源 —— 我们的 `first_live_seq()` 同名同义。
- **request/header 的恢复快照**：恢复时记一次 reason=resume 的请求头快照
  （s07 的机制在会话边界的应用）。
- **checkpoint 策略**：谁负责"每 N 步强制落盘"是一个独立插件。
