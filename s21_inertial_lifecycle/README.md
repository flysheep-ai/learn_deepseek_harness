# s21 — 惯性生命周期（Inertial Lifecycle）

**English version: [README.en.md](README.en.md)**

[s20](../s20_reactive_coeffects/) → **s21** → [s22](../s22_session_lifecycle/)

> 生命周期不该由 load/unload 命令驱动，
> 而该由「实际是什么样」和「应该是什么样」的**比较**驱动。
> 而且转换一旦开始，就**跑完再响应**新的目标变化 —— 这叫惯性。

---

## 上一章留下的问题

s20 的组件只有 idle/active 两态，转换是瞬时的。真实系统里：

- 一次激活要执行很多效应（可能很慢、可能失败）
- 转换进行到一半，依赖又变了 —— 停下来还是跑完？
- 转换失败会留下什么？半个激活的组件？

## 这一章解决什么

把 Cordis 论文 §4.2/§4.3 的生命周期机制做成教学版：

```
INACTIVE → RELOADING → ACTIVE → UNLOADING → INACTIVE
               ↑            │
               └── 链式切换 ──┘
```

核心是**两个视图**：

```
target     应该是什么样：⊥ = 不该跑；否则是"每个声明 key 由谁提供"的解析
committed  实际激活时承诺的解析
```

所有规则都由两者的比较驱动。

## 新增的核心概念

### 1. 比较驱动，不是命令驱动

refresh() 重算 target → 和 committed 比 → 不同就启动转换。
不是你调用了 load/unload，而是"实际 ≠ 应该"这个事实本身触发了转换。
命令只是改变 target 的输入（retire / provide / unprovide）。

### 2. 惯性（inertia）

转换在途时 refresh 只**记下**新目标，不打断；转换跑完的那一刻再比一次：
目标又变了 → **链式**进入下一个转换。

### 3. 失败：先恢复，再记录，不传染

```
setup 失败
  → 把已构建的累加器全部跑掉（回到"什么都没装"）
  → 错误记录在 fiber 上
  → 走和正常卸载同一条 unload 出口
```

失败组件对状态的贡献为零；错误**不传播**给父组件；兄弟组件照常运行 ——
这正是插件宿主想要的行为。

### 4. 失败的 fiber 不重入

论文里 L-Begin 的前提是 INACTIVE(⊥)；失败结果是 INACTIVE(ξ)，
不会自动重试 —— 对环境不变的重试只会再失败一次，等**人**干预。

## 为什么这样设计

**为什么"应该 vs 实际"比命令更稳**：命令式（`component.load()`）要求每个
调用方都判断"该不该加载"；比较式把判断集中在一个地方（refresh），调用方
只负责改事实（retire / provide），**不会出现"忘了调用"或"重复调用"**。

**为什么失败要走同一条 unload 出口**：如果失败走独立的错误路径，就得维护
两套清理逻辑，而且"失败时清理到什么程度"会变成一个没有答案的问题。
走同一条出口：**每个结果只能通过 L-Unload 到达**，失败组件的贡献为零是
免费的推论。

## 与 s20 相比发生了什么

| | s20 | s21 |
|---|---|---|
| 组件状态 | idle / active 两态 | **四态 + 中间态** |
| 转换 | 瞬时同步 | **惯性：跑完再响应** |
| 转换失败 | 未处理 | **先恢复、再记录、不传染、不重入** |
| 驱动方式 | provide/unprovide 直接改状态 | **target vs committed 比较** |
| retire 与 remove | 无 | **分离**（先请求，规则执行到位） |

## 真实系统里还有什么

- **迭代器效应**：真实 reload 把 setup 拆成多步，每步之后检查目标是否过期
  （staleness check），过期就中止——部分构建靠累加器回滚（论文 §4.3.2）。
- **异步转换 + inertia 句柄**：`fiber.inertia` 是进行中转换的句柄，
  与 UI 的取消/进度联动（dsh Algorithm 5）。
- **Confluence 定理**：这套机制加上独立性、totality 之后，动态历史收敛到
  静态装配——论文定理 73 的工程意义。

## 自己动手改

1. 把 `_begin_reload` 的 setup 拆成三步（每步一个效应），在第二步之前改
   target，观察累加器回滚。
2. 让失败组件在 target 变化后重试（取消"不重入"），对比两种行为对
   "环境已修复"场景的差别。
3. 给 unload 加上 s20 的三段顺序（守卫等待依赖者），把两章的机制拼起来。
