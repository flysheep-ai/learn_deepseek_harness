## 一、这篇论文在回答什么问题

现代软件越来越需要在**运行时**装载、卸载、替换组件：

- 插件系统（VSCode、浏览器扩展）
- 自演化的 Agent Harness（AI 生成自己的工具、替换自己的组件）
- 长期运行的服务进程

但动态组合的**形式化基础**几乎不存在。静态组合有完整的类型理论（函数调用、模块导入、类继承都是编译期解决且终身固定的），动态组合却只有工程上的权宜之计。

论文用 VSCode 的数据说明权宜之计有多粗糙：

> 安装量前 100 的扩展中，**87 个包含可执行代码**，移除它们需要重启宿主。
> `deactivate` 钩子只在宿主进程终止时优雅关闭，**不能热卸载**；
> 而且它把"效应的清理"和"效应的创建"（在 `activate` 里）**分离在两个函数**里。
>
> 只有 7 个扩展声明了 `extensionDependencies` —— 因为扩展 API 鼓励
> 通过固定的宿主扩展点贡献能力，扩展之间的依赖"结构上不存在"；
> `getExtension(...).exports` 返回 `any`，连一个可检查的接口都没有。

两个问题的本质，论文概括为**正交的两个维度**：

| 维度 | 问题 | 形式化语言 |
|---|---|---|
| **时间**（temporal） | 移除组件时，它对共享环境做的修改必须被完全、安全地逆转 | 效应（effect） |
| **空间**（spatial） | 组件之间的依赖必须被声明、发现、结构化地解析，并在依赖变化时作出反应 | coeffect |

而现有做法（重启进程 / 容器编排）是两个维度上的**粒度错配**：它们都工作在进程与容器的边界，现代系统却需要在更细的粒度上组合。

## 二、理论基础：把效应和 coeffect 从编译期抬升到运行时

论文的理论起点是两类经典类型系统概念：

- **效应系统（effect systems）**：`Γ ⊢ t : Tₑ` —— 在结果类型上标注"这段计算会产生什么副作用"。
  源头是 Lucassen & Gifford（1988），后来发展为 Moggi 的单子效应、
  Plotkin & Power 的代数效应与 effect handlers。
  **效应描述"程序如何修改世界"。**

- **Coeffect 系统（coeffect systems）**：`Γᶜ ⊢ t : T` —— 在**上下文**上标注"这段计算需要环境提供什么"。
  Petricek 等人（2014）用余单子（comonad）统一了上下文依赖分析；
  分级 coeffect 用半环精确追踪资源用量（0 = 不用，1 = 线性，n = 有界，∞ = 无限制）。
  **Coeffect 描述"世界对程序的约束"。**

关键的观察是这两条线的对称性：

> 效应 = 计算**修改**环境的方式 → 正好是 temporal composability 要管的事
> coeffect = 计算**依赖**环境的方式 → 正好是 spatial composability 要管的事

但经典理论都是**静态工具**：效应在词法固定的作用域内被 handler 释放，
coeffect 注解在执行前就对固定上下文验证完毕。

而动态组合需要的是：**对运行时到达、运行中不断变化的上下文，
提供这些静态系统所提供的保证。**

论文的选择不是给类型系统加更多注解，而是把这两个概念**物化（reify）成运行时可以直接操作的结构**：

> 与其扩展静态类型系统，不如把 effect 和 coeffect 的概念结构物化出来，
> 让运行时直接对它们进行操作，在动态场景下建立静态系统提供的那些保证。

## 三、核心贡献一：可逆效应（Revertible Effects）

### 3.1 把"修改"变成"带逆的修改"

一个效应被建模为：

```
Γ → Γ × (Γ → Γ)
```

读作：输入当前上下文，返回**修改后的上下文** + **一个显式的逆函数**。

三个设计决策都在这个类型签名里：

1. **逆由调用者在效应施加处提供**（而不是预先登记）。因为一个逆往往只在
   它作用的那一个状态下才成立 —— `close` 只能关"这个文件描述符"，
   必须由 `open` 返回，不能事先写在注册表里。

2. **逆只需要单侧成立**：只要求 `g(δ) = γ`（逆能把"施加后的状态"带回"施加前的状态"），
   不要求 `f(g(x)) = x`。undo 一件事就够了，不需要"undo 之后再 redo 还是原样"。
   这个放松对工程现实至关重要 —— `free` 之后堆布局不可能复原，但"回收了资源"已经够了。

3. **效应应用返回的东西由运行时追踪**。施加效应时，运行时把逆复合进一个
   **累加器（accumulator）** `φ`。这就是 track：

```
track(f, g)(γ, φ) = (f(γ), φ ∘ g)
```

### 3.2 扭曲复合：逆以反序累积

多个效应复合时，逆必须以**相反顺序**累积：

```
(f₁, g₁) ⊛ (f₂, g₂) = (f₁ ∘ f₂, g₂ ∘ g₁)
```

这是整篇论文里最"免费"但也最重要的结构性质：**逆的复合不需要编写任何代码**。
作者只需要为**每个原子效应**手写一个逆，任意复合的逆由组合自动推导。

> 对比 React 的 `useEffect`：它把效应和 cleanup 结构上配对在一起了，
> 但 hook 只能在组件顶层调用、不能嵌套、不能异步、不能迭代 ——
> **效应无法从其他效应组装**，所以复合逆无从推导。
> Cordis 效应是普通运算，自由组合、可异步，复合逆零成本。

### 3.3 recover 与"健全不变量"

恢复（recover）就是：应用累加器 `φ` 到当前状态，然后重置累加器。

一条核心不变量贯穿全篇 —— **健全不变量（soundness invariant）**：

```
φ(γ) = γ₀     "累加器作用于当前状态 = 组件装载前的初始状态"
```

每个效应施加（track）都保持这条不变量不变；于是**完整恢复是一个结构保证**，
不是"只要作者把 cleanup 写对了"。

### 3.4 独立性：乱序撤回

单组件的逆是 LIFO 顺序撤回，不需要任何额外条件。但真实系统里：

- 多个组件的效应**交错**发生，各自持有自己的逆；
- 撤回一个组件时，它的逆会遇到**被别的组件移动过的状态**。

此时逆是否仍成立，是一个**交换性（commutation）**问题。

论文定义：两个效应**独立（independent）**，当且仅当一个效应的所有变换
（正向映射 + 它产生的所有逆）与另一个效应的所有变换两两交换。
对"由 (f, g) 诱导"的效应，独立 = 四对函数交换（f₁f₂, g₁g₂, f₁g₂, g₁f₂）。

在独立性下，**逆可以按任意顺序撤回**（推论 21：n 个逆按任意排列应用都回到初始态）。
这直接对应"从运行中的系统里撤下一个组件"。

### 3.5 观察等价：恢复的"相等"意味着什么

物理状态不可能逐位复原（`free` 不回堆布局；生成的名字不复原）。
所以第 3 节的相等全部**读作一个等价关系 ≃** —— **观察等价（observational equivalence）**：

> 两个状态相关，当且仅当**没有观察者能区分它们**。

而这个观察者被赋予的能力，正好是 coeffect —— 每个 key 携带自己的等价关系，
上下文的等价由它们组装。**coeffect 定义了效应在什么粒度上"算恢复了"**。
这是两个维度第一次、也是结构性的一次交汇：

> **coeffect 给 effect 的独立性提供弹药。**

## 四、核心贡献二：反应式 Coeffect（Reactive Coeffects）

### 4.1 把 IoC 容器形式化成 coeffect 上下文

coeffect 上下文就是一个依赖偏函数：

```
Σ = (k : K) ⇀ 𝒱 k
```

组件声明一个**规格（specification）** `d`：一组 key（+ 对每个 key 的值类型约束）。

每个 key 上有一个可容许的等价 `≃ₖ`（哪些值对这个 key 的使用者不可区分）。
规格的满足（satisfaction）定义为：

```
σ ⊧ d   ⟺   dom(d) ⊆ dom(σ) 且 每个键的值类型可容许
```

### 4.2 把上下文变化分类成三种

这是"反应式"这个词的来源。对任何一次上下文变化，把它**对照组件规格分类**：

```
notify_d(σ, σ′) = activating    σ ⊭ d 且 σ′ ⊧ d     （依赖刚被满足 → 激活）
                = deactivating  σ ⊧ d 且 σ′ ⊭ d     （依赖刚被撤走 → 停用）
                = neutral       其余                  （与此组件无关）
```

传统 IoC 容器的依赖注入是"初始化时布线一次"；反应式 coeffect 的要求是
**每次上下文变化都要对照规格重新判定**。

> 分类对照规格这件事是"检测出满足性变化"的机制；
> 响应分类是"驱动激活与停用"的机制。
> 合起来：**正确的 coeffect 排序成为一种结构保证**，
> 而不是开发者"记得在依赖变化时通知下游"的自觉。

### 4.3 隔离（isolation）与拦截（interception）

两个进阶操作，都建立在"派生上下文"上：

- **isolate(k, realm)**：给 key 绑定一个 realm 符号。
  两个上下文给同一个 key 不同的 realm → 它们解析到**互相独立**的绑定。
  这是"per-agent 工具变体"这类需求的根源。

- **intercept(k, metadata)**：在上下文上挂载元数据。
  组件读 key 时，**组件声明的元数据**与**上下文携带的元数据**按 key 自己的语义合并，
  且**上下文一侧右偏（优先级更高）**：

> 让**外层上下文**在不修改组件的前提下约束组件如何使用一个 coeffect。
> 例如给社区组件只读的数据库访问，而核心组件保留完整权限。
> 拦截只改变"如何调用依赖"，不改变"依赖是否满足"，
> 所以**运行时安装/重配置/移除拦截都不会触发任何重载**。

## 五、统一上下文：Γ∞ —— 一种编程范式

把效应上下文（状态 + 累加器）和 coeffect 上下文合并，得到递归的自相似类型：

```
Γ∞ = μΓ. Γ × (Γ → Γ) × Σ
       状态   累加器   coeffect 上下文
```

三层含义：

1. **Σ 吸收一切共享状态**。底层类型族 𝒱 不受约束，所以任何需要跨组件共享的状态
   都可以编码成一个带合适值类型的依赖。**组件与环境的一切交互都经过这一个实体。**

2. **递归结构支持分层控制**。父上下文聚合多个子层的效应，形成树状控制结构 ——
   字面意义的"插件"隐喻：

   > 装载组件 = 执行它的效应（plugging in）
   > 卸载组件 = 恢复它的效应（unplugging，不影响其他运行中的组件）
   > 不同层的组件独立装卸；父上下文管理所有子层的效应，支持任意嵌套。

3. **范式声明**：效应通过上下文修改世界，coeffect 通过上下文声明约束，
   两者共享同一个可操作的一等实体。这就是论文标题里的
   **"A Programming Paradigm for Spatiotemporal Composability"**。

## 六、组件演算：十规则与 fiber

### 6.1 fiber = 组件的一个运行实例

```
fiber = ⟨d, p, e, π, σ, θ⟩
        │  │  │  │  │  └─ 生命周期状态
        │  │  │  │  └──── 自己的键值表（它安装的绑定）
        │  │  │  └─────── 父 fiber（注册者）
        │  │  └────────── 效应函数
        │  └───────────── 它可能提供的键（provision）
        └──────────────── 它声明的依赖（specification）
```

几个刻意的设计：

- **名字是原子（生成性名字）**：fiber 的身份在它自己的状态突变中存活；
  任何规则都不计算、检查名字的结构，只做相等比较。

- **coeffect 上下文是派生的，不是存储的**：`σ_γ = 活跃 fibers 各自表的并集`。
  一个 fiber 停止提供（进入 UNLOADING）**先于**它撤回任何东西 ——
  这让依赖者提前一步看到"不可满足"，开始自己的 teardown。

- **单源纪律**：每个 key 只有一个可能的提供者（插入时检查 provision 不相交）。
  没有这条，下面的 target/committed view 对比就没有意义。

### 6.2 target view vs committed view：整个生命周期的引擎

每个 fiber 有一个 **target view**（它"应该"跑成什么样：⊥ = 不该跑，
否则是"每个声明 key 由哪个 fiber 提供"的解析）和一个 **committed view**
（它实际激活时用的是什么解析）。

**所有生命周期规则都由这两个 view 的比较驱动**：

```
target = ω（承诺的）且 fiber 未安装 → L-Reload（装载）
target ≠ ω（承诺的）且 fiber 已安装 → L-Unload（卸载）
```

注意 target 记录的是**提供者 fiber** 而不是值 —— 这是让比较可用的关键：
一个不同的 fiber 提供相等的值必须被视为"换了提供者"（uid 从新生成、永不复用）。

### 6.3 三条编排规则 + 七条生命周期规则

编排（orchestration）是唯一的外部输入：

```
O-Insert   插入一个 fiber（唯一的新鲜名字，provision 不相交）
O-Retire   置 retire 标记（请求停止存在 —— 注意：是请求，不是强制）
O-Remove   删除 fiber（前提：已 retire、已 INACTIVE、无子 fiber）
```

**retire 与 remove 的分离**是整章最有工程味道的设计之一：

> 一个已 retire 但仍 ACTIVE 的 fiber 必须**先被停用**；
> 提前移除它会丢弃累加器（accumulator）而泄漏资源。
> retire 是无条件请求；生命周期规则负责把它执行到位。

生命周期规则（L-Begin / L-Iter / L-Finish / L-Divert / L-Raise / L-Leave / L-Unload）
实现了带**中间态**的状态机：`INACTIVE → RELOADING → ACTIVE → UNLOADING → INACTIVE`，
因为真实运行时里一次转换不是原子的、即时的、不会失败的。

- **L-Raise**：效应迭代失败 → 走 UNLOADING 路径**先恢复再记录错误**。
  于是"失败"和"正常停用"经过同一条 L-Unload 出口 —— 一个失败组件的贡献为零（推论 62）。
- **失败记录在 fiber 上而不是传播给父组件**：一个组件转换失败，它的兄弟继续运行 ——
  这正是插件宿主想要的行为。

### 6.4 限制（Confinement）

效应函数必须被**限制在自己的 fiber 内**：

- 只能写自己 fiber 的表（+ 注册子组件的条目）
- 只能读**自己声明的** coeffect，以及自己表的键值
- 不能读任何控制字段（不能根据别的 fiber 的生命周期状态分支）

限制是 metatheory 的前提：它保证 Table 1（十条规则作为"谁写了什么"的完整清单）
真的是**完整的**清单。

### 6.5 实例化（Instantiation）：组件注册子组件

组件在安装自己的效应时，可以注册一个子组件；**它产生的逆是 O-Retire 而不是 O-Remove**。

原因很微妙：逆必须在它被到达的任何地方都能应用。O-Remove 有前提
（子 fiber 必须已 INACTIVE），由它构造的逆可能失败 ——
而逆必须总是能跑。O-Retire 唯一的前提是 fiber 存在。

> 卸载一个父组件 → 累加器运行 → retire 所有子组件 → 子组件的生命周期规则
> 再把它们逐个带下去 → 孙组件逐层到达（定理 66 级联）。

## 七、Metatheory：五个定理，把保证从单个组件带向整个系统

metatheory 的目标一句话：**一个组件的保证，无论其他 fiber 在其间做了什么，都成立。**

| 定理 | 内容 | 直觉 |
|---|---|---|
| **Preservation**（定理 59/61/62） | 每条规则保持良构；失败 fiber 对状态的贡献为零 | "不会出现半吊子状态" |
| **Temporal**（定理 63） | 一个 fiber 在其整个 episode 中读同一个解析；提供者的撤回**等到**依赖者停用之后 | "依赖者不会读到半撤的依赖" |
| **Spatial**（定理 64） | 效应迭代间的 staleness 检查保证每次迭代都作用于"它被期望作用的状态" | "效应不会作用在过期的世界上" |
| **Progress / Termination**（定理 66） | 在良构 + 声明无环 + 有界迭代下，系统一定到达 quiescence（安静点） | "不会死锁、不会活锁" |
| **Confluence**（定理 73） | 到达的安静点 = **静态装配**会产生的那个配置；与调度顺序无关 | "动态历史不留痕迹" |

Confluence 定理是全文的高潮，值得展开：

> 无论一个运行中的系统经历了什么激活/停用序列，
> 它安静下来的状态，与"每个最终活跃的组件按依赖顺序只装载一次、
> 从不卸载"所得到的状态相同。
>
> 这是动态组合的"与从零求值一致"——增量计算里 change propagation
> 对一致性承诺的对应物。

它让组件作者可以**把 Cordis 应用当作静态装配来推理**：
编排者随意增删组件、替换 provider、回退替换 ——
最终状态等于"一开始就把最终组合写下来"。

两个诚实的分界：

1. **失败被排除在 confluence 之外**。不同调度可能让一个 fiber 失败而另一个调度让它成功
   —— 这是真实的发散来源。但失败 fiber 的贡献为零，所以发散**仅限于**它的生命周期状态。
2. 定理保证的是**状态**，不是过程中的**排放（emission）** ——
   这就是第 6.1 节"获取（acquisition）在边界内、排放跨出边界"的区分。

## 八、实现：Cordis 的三层

### 8.1 理论与实现逐项对照

论文给了完整的对照表（Table 2）。挑最重要的几行：

| 理论 | 实现 |
|---|---|
| Γ∞ | `ctx`，一等上下文 |
| effectΓ(e) | `ctx.effect(callback)` —— 回调返回逆 |
| get(k) / set(k, v) | `ctx.get(key)` / `ctx.set(key, value)` |
| isolate / intercept | `ctx.isolate(key, realm)` / `ctx.intercept(key, metadata)` |
| O-Insert / O-Retire | `ctx.use` 和它回调返回的逆 |
| fiber.θ（生命周期） | `fiber.state`，LOADING 即 RELOADING |
| recover / accumulator | `fiber.dispose`，累加器 |
| target(γ, n) | `fiber.target`，refresh 重算 |

### 8.2 三个关键算法的直觉

**Algorithm 4（实例化）**：

```python
def use(ctx, component, config):
    callback = lambda: refresh(fiber)         # 执行 = 启动子组件生命周期
    inverse  = lambda: (target := ⊥, unload(fiber))   # 恢复 = 强制目标为 ⊥ 并卸载
    ctx.effect(callback, inverse)             # 实例化 = 父上下文里的一个普通可逆效应
```

**实例化是一个普通的被追踪效应** —— 所以卸载父组件自动级联到子组件，
不需要任何"父子关系"的额外机制。

**Algorithm 5（生命周期）**：惯性状态机。两个关键点：

1. `refresh` 标记 `UNLOADING` **在创建卸载任务之前**（L-Leave）—— 先停止提供，
   让依赖者在任何逆被调度之前就重算 target。
2. `unload` 先 `await` 所有被通知的依赖者达到 INACTIVE（L-Unload 的守卫），
   再运行 `fiber.dispose`（累加器）。Provider 图按需遍历，不预先分析。

**Algorithm 6（Proxy 访问）**：沿 fiber 链向上走，
第一个在 committed view 里绑定 key 的 fiber 授权访问。三种失败：

- 声明了 key 但没 commit → INACTIVE_ACCESS（组件没装载）
- 走到根都没声明 → UNDECLARED_ACCESS（未声明的访问）

> `ctx.get(key)` 只查存储、返回"有或没有"、从不失败；
> Proxy 解析的是**访问者自己的 view**，在**使用点**强制 coeffect 规格。
> 这正是 capability-based security 的形态：inject 声明 = capability 请求，
> context proxy = capability 中介。

### 8.3 加载器：配置调和 + 事务性热替换

核心库面向组件作者（命令式原语）；加载器面向编排者（声明式配置）。

- **配置调和**：持久化配置 = 期望的组合。每次配置变化，加载器 diff 出
  entry 的新增/删除/替换，映射到 fiber 的 use/retire。
- **事务性 HMR**（Algorithm 10）：先备份并失效模块缓存 → 逐个换新 fiber →
  任何一个 import 失败 → **恢复缓存 + 从备份重建全部**。

> 系统永远不会进入"换了一半"的状态。

### 8.4 Case study：Koishi

Koishi 是一个基于 Cordis 的聊天机器人框架，**4000+ 社区插件**：

- **时间维**：控制台禁用插件 → 效应原位撤回；HMR 保存即重载，
  其他组件的缓存和连接不受影响。**作者不必写 uninstall 路径** ——
  上下文介导的效应自动获得有序清理。
- **空间维**：IM 适配器提供平台访问、数据库驱动提供持久化、
  功能插件声明它们为 coeffect —— 真实存在的依赖拓扑，而且
  **插件和依赖通常由不同作者编写，他们唯一共享的就是那个 coeffect**。

## 九、和我们的 learn-deepseek-harness 对照

这篇论文读起来应该非常亲切 —— 因为本课程 s13/s14 就是它的极简教学版：

| Cordis（论文） | 我们的课程 | 关系 |
|---|---|---|
| 可逆效应：注册返回逆 | s14 `on()/use()` 返回注销函数、`PluginContext._disposers` 逆序执行 | 同一机制的最简形式 |
| 反应式 coeffect：对照规格分类 | s14 `ctx.require()` 缺失时早失败 | 我们只做了"装载时检查"，没有"变化时重判" |
| unified context Γ∞ | s14 `Harness`（services + tools + prompts + bus） | 结构相似，但我们的 service 不携带依赖规格 |
| fiber 生命周期 + 惯性状态机 | 无（我们的插件没有中间态、没有异步转换） | 论文第 4.3 章是我们没走的路 |
| single-source 纪律 | s14 `provide()` 重名即抛错 | 完全对应 |
| intercept（上下文右偏） | 无 | 值得补的机制 |
| isolate（realm） | s09 `registry.restricted()` | 相近思想（per-agent 工具集） |
| Confluence 定理 | 无（我们也无法证明——没有形式化） | 论文的分界线：工程 vs 科学 |
| 惰性/guard：提供者先停供、等依赖者停用 | 无 | s13/s14 没有跨组件依赖拓扑 |

三个最值得从论文带回工程实践的洞察：

1. **"注册返回逆"我们已经做了**（s14 的核心机制正是论文 track/recover 的特例）。
   论文告诉你它的名字：**可逆效应**，以及它为什么是对的 —— 因为
   "每个原子效应手写逆、复合逆自动推导"是**局部性**问题的正解。

2. **"依赖变化时重新判定"我们没做**。我们的插件在装载时 `require`，
   之后依赖被卸载就没人管了。论文的 reactive coeffect + notify 分类
   （activating/deactivating/neutral）是这部分的最小正解。
   在 s14 的课程语言里它就是：**provide/unprovide 事件 + 依赖者自动重装载**。

3. **"先停供、再撤回、最后等依赖者"的三段顺序**（L-Leave 先于 L-Unload，
   L-Unload 等依赖者）解决了一个我们课程里从未暴露的问题 ——
   因为我们没有跨组件的依赖拓扑。一旦有（s16 的团队成员之间有！），
   这个顺序问题就会真实出现。

## 十、论文留下的开放问题（与我们最相关的那个）

结论章点名了未来验证方向：

> 超越人工维护的插件生态，一个令人信服的方向是**自演化的 Agent Harness** ——
> AI 持续生成和替换自己的 harness 组件，几乎没有人工监督。
> 在那种设定下验证 Cordis，将同时验证：
> - 快速组件替换下的完整恢复（时间保证）
> - 频繁拓扑变化下的依赖协调（空间保证）

这正好是本课程最后一章（s18）立下的那个愿景的另一面：

> Agent 的智能主要来自模型；Harness 的价值是为模型构建
> 一个拥有工具、环境、上下文、状态、权限和反馈的可操作世界。

如果有一天这个"可操作世界"需要**由模型自己改装**（模型给自己的 harness 加工具、
换策略、重建依赖），那 Cordis 论文就是改装操作的形式化说明书：
什么样的修改可以安全撤回（时间维）、什么样的依赖变化必须通知谁（空间维）、
以及什么样的调度顺序最终收敛到与静态装配一致的状态（confluence）。
